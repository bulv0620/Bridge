# Spec 驱动迭代流程

Spec 用来定义一次变更的意图、边界和可验证结果。它不替代领域文档，也不要求所有小改动都走
完整审批流程。

## 任务分级

### S：直接实现

适用于影响明确、容易回退且不改变重要行为的改动：

- 文案、图标、颜色、间距和局部布局。
- 根因明确的局部 Bug。
- 不改变外部行为的简单清理。
- 仅修正文档漂移。

S 级不要求独立 Spec，但任务描述必须包含目标、保持不变项和验证方式。调查后发现涉及 IPC、
持久化、跨平台或高风险行为时，升级为 M/L。

### M：简短 Spec

适用于：

- 用户可观察的交互或功能调整。
- 局部新功能。
- IPC 参数或共享状态变化。
- 涉及多个组件/进程的 Bug。
- 中型重构或有明确指标的性能优化。

使用 [`templates/change.md`](templates/change.md)。

### L：完整 Spec

适用于：

- 同步判断、删除、覆盖、冲突、失败恢复。
- 网络协议、文件接收路径、剪贴板或凭据。
- 持久化 schema 和数据迁移。
- 新的核心产品能力或大型架构调整。
- Electron 大版本、更新/签名/发布流程变更。
- 任何可能造成数据损失或扩大系统权限的改动。

使用 [`templates/change.md`](templates/change.md) 的全部章节，并在用户明确批准后才实现。

## 任务类型与默认交互

| 类型          | 第一阶段                     | 何时开始实现                |
| ------------- | ---------------------------- | --------------------------- |
| 原因未知 Bug  | 只读调查、复现、根因和影响面 | 用户接受修复方向后          |
| 原因明确 Bug  | S 可直接实现；M/L 先写 Spec  | 范围明确或 Spec 批准后      |
| UI/交互优化   | 明确体验目标和全部状态       | S 直接；行为变化需 Spec     |
| 现有功能调整  | 对比旧/新行为和保持不变项    | Spec 批准后                 |
| 新功能        | 调研、产品选择、非目标       | Spec 无未决阻塞项并批准后   |
| 重构          | 建立外部行为基线             | 有迁移计划和回归证据后      |
| 性能优化      | 先测量基线和瓶颈             | 有量化目标后                |
| 安全审查      | 先只读评估威胁与证据         | 明确授权修复后              |
| 依赖/平台升级 | 迁移影响和回退评估           | 目标版本和验证矩阵批准后    |
| 发布          | 先准备候选检查               | 创建 tag/发布需单独明确授权 |

## Spec 生命周期

```text
Draft → Approved → Implementing → Verified → Archived
          │              │
          └──────────────┴→ Superseded
```

- **Draft**：正在讨论，允许修改，不授权业务实现。
- **Approved**：目标、非目标和验收标准已由用户确认。
- **Implementing**：正在实现；实现发现需求缺口时回到 Draft/Approved 处理。
- **Verified**：已逐条验收，失败项为零；允许存在明确记录的 `Not Verified`。
- **Archived**：稳定规则已沉淀到长期文档，Spec 移至 `archive/`。
- **Superseded**：被另一份 Spec 或正式决策取代。

只有用户或任务中明确指定的负责人可以把 L 级 Spec 从 Draft 改为 Approved。Agent 不得自行批准
涉及产品、安全或数据语义的选择。

## 文件规则

```text
docs/specs/
├── active/
│   └── YYYY-MM-DD-short-name.md
├── archive/
│   └── YYYY/
└── templates/
```

- 使用小写英文短横线文件名，日期采用创建日期。
- 一个 Spec 只描述一个可独立验收的变更。
- Spec 内使用稳定的 `REQ-01` 和 `AC-01` 编号。
- 代码、PR 或提交可以引用这些编号。
- 不在 Spec 中复制大段实现代码；技术设计只写约束、接口和关键取舍。

## 每阶段的 Agent 行为

### 调查

- 阅读现有代码、长期文档和相关历史。
- 区分已证实事实、推断和未知项。
- 不修改业务代码。
- 输出影响面、风险、产品决策和技术决策。

### 起草

- 明确目标与非目标。
- 把用户可观察行为写成 MUST/SHOULD/MAY 或决策表。
- 为异常、取消、失败、跨平台和安全定义结果。
- 验收标准必须能判定 Pass/Fail。
- 未确定内容进入 Open Questions，不擅自补全。

### 实现

- 严格遵循 Approved Spec。
- 不影响外部行为的局部技术细节可自主决定。
- 需要改变用户行为、数据格式、安全边界或范围时暂停并报告。
- 同步更新测试、i18n 和长期文档。

### 验收

- 对每条 AC 标记 Pass、Fail 或 Not Verified，并提供证据。
- 不修改 Spec 来迁就实现。
- 验收发现失败后，等待修复授权或按原任务明确授权修复。
- 按 [`../quality/verification.md`](../quality/verification.md) 运行适用检查。

### 归档

- 将可长期复用的规则更新到 `behavior/` 或 `architecture/`。
- 记录实现偏差、未验证项和关联 ADR。
- 状态改为 Verified 后移至年度 archive。
- 归档不自动授权 commit、push 或 release；用户明确授权后按
  [`../operations/release.md`](../operations/release.md) 执行。

### 提交与发版

- 用户说“提交”时，只创建当前逻辑修改的普通 commit。
- 用户说“提交并推送”时，创建普通 commit 并 push，不创建版本。
- 用户说“提交并发版”时，可以连续执行普通 commit、push、`npm run release`、release
  commit/tag push 和 Actions 跟踪。
- Agent 在执行前仍需满足 Spec、验证、分支、工作区和远端同步条件。
- 多个普通 commit 可以共同进入一次 release，不要求每个 commit 都生成版本。

## Spec 可以省略的情况

以下情况通常不创建 Spec：

- 纯调查或评审，没有授权修改。
- 一处明确文案/样式修正。
- 恢复已经由现有文档或测试清楚定义的行为。
- 机械更新生成内容或版本号。

但“改动很小”不等于低风险。同步一行方向判断、一个接收路径拼接或一个 IPC 暴露即使代码很少，
也应按 L 级处理。
