## 背景

当前共享页面一次只能选择和发送一个文件。发送端先向
`POST /api/upload/request` 提交单文件元数据；接收端为每个请求显示一次原生确认对话框，允许后再
通过 `POST /api/upload/:uploadId` 接收文件。

用户已明确选择新的产品方向：

- 一次选中的一批文件只确认一次。
- 软件仍处于测试期，必要时可以不兼容旧版文件传输协议。
- 不只增加批量能力，还要修复现有链路中影响可靠性和安全性的问题，以新的安全链路替换旧链路。

只读代码调查确认当前链路存在以下问题：

- 请求流被两次 `pipe` 到同一个写入流，可能造成内容重复写入。
- 文件元数据只做真值判断；没有严格校验类型、范围、文件名、设备字段和批量元数据大小。
- 保存路径直接由不可信文件名参与拼接，缺少跨平台文件名校验和下载目录边界证明。
- 声明的大小只用于展示进度，没有对 `Content-Length` 和实际接收字节数做一致性校验。
- `uploadId` 在上传完成前可被重复或并发使用，也没有来源绑定和过期时间。
- 同名文件名只通过“检查后使用”选择，多个待传文件之间存在预留竞态。
- 中断或写入失败会留下部分文件。
- HTTP 服务启用了通用 CORS，扩大了浏览器页面向局域网服务发起请求的攻击面。

本变更提高局域网文件传输的授权与落盘安全性，但不增加设备认证、配对、TLS 或端到端加密。

## 目标

- 允许用户一次选择多个普通文件，并向一个在线设备作为一个批次发送。
- 接收端在整批元数据通过校验后只显示一次原生确认。
- 用新的批量授权和上传协议完全替换现有单文件上传 endpoint。
- 严格限制网络元数据、授权、请求体长度和接收路径，防止覆盖、路径逃逸、重放及部分文件残留。
- 保持批内文件相互独立：单个文件失败或取消时，其余已授权文件仍可继续。
- 为主要安全规则提供可重复的纯逻辑边界，便于后续补充自动化验证；本次按用户要求不新增或运行
  自动化测试。

## 非目标

- 设备身份认证、可信设备配对、TLS、端到端加密或内容级加密。
- 文件夹传输、递归目录、空目录或相对目录结构。
- 断点续传、失败文件自动重试、传输事务或整批原子提交。
- 内容哈希、恶意内容扫描、磁盘配额管理或用户可配置的文件大小上限。
- 与旧版 `file-push` endpoint 的兼容或自动降级。
- 改变剪贴板共享协议、发现端口、HTTP 端口或设备发现版本。
- 持久化发送、接收或授权历史。

## 当前行为

- 发送端一次只能选择一个文件。
- 用户点击设备后，该文件的元数据作为一个请求发送。
- 接收端每个请求弹一次确认，接受后立即创建一个 `uploadId`。
- 文件 body 直接写入最终下载路径。
- 同名文件使用 `name (1).ext`、`name (2).ext` 递增，但没有跨待处理请求预留文件名。
- 失败、取消、长度不符和重复上传没有完整、统一的终态处理。

## 目标行为

- REQ-01：发送端 MUST 允许一次选择多个普通文件；一次选择得到的非空文件集合，以及之后选择的
  同一目标设备，共同定义一个批次。选择文件夹不在本次范围内。
- REQ-02：发送端 MUST 在发送批次前提交一次批量元数据请求。接收端 MUST 先完整校验请求，再显示
  一次且仅一次原生确认；非法请求 MUST 在不显示对话框的情况下拒绝。
- REQ-03：确认对话框 MUST 显示来源设备名、文件数、总大小和有界的文件名摘要；中英文文案 MUST
  同步。过长文件列表不得造成不可操作的对话框。
- REQ-04：用户拒绝批次时，接收端 MUST 不创建上传授权、临时文件或最终文件；发送端 MUST 将该
  批次的文件记录为被拒绝，而不是网络故障。
- REQ-05：文件传输能力 MUST 改为 `file-push-v2`。新版 MUST 只向声明该能力的设备发起批量传输，
  MUST 不广播旧 `file-push`，也 MUST 不保留旧上传 endpoint 或回退链路。
- REQ-06：已有设置中的 `file-push` MUST 在新版第一次读取时迁移为 `file-push-v2`，保留用户原来
  的“文件接收”开关意图；降级到旧版后无需保证新版能力可用。`clipboard` 等其他能力 MUST 保持
  不变。
- REQ-07：发现协议版本、UDP/HTTP 端口和剪贴板协议 MUST 保持不变。因此新旧设备仍可发现彼此并
  在共同支持时共享剪贴板，但不得进行跨版本文件传输。
- REQ-08：批量请求 MUST 使用固定的新 endpoint 和明确的协议版本。每个文件 MUST 有批内唯一的
  非秘密标识；接收端批准后 MUST 为每个文件签发不可预测的上传令牌。
- REQ-09：上传令牌 MUST 通过请求头传递，MUST 绑定请求批次、文件和批准请求的来源 IP，MUST
  只能成功开始一次。重复、并发、错文件、错批次、错来源或已过期的使用 MUST 在创建文件前拒绝。
- REQ-10：尚未开始的上传授权 MUST 在 10 分钟后过期并从接收任务中移除。上传开始后不受该 10
  分钟限制。服务停止时 MUST 使全部未使用授权失效，并终止活动写入。
- REQ-11：批量 JSON body MUST 限制为 256 KiB；每批 MUST 包含 1 至 256 个文件。文件大小 MUST
  是 `0` 至 `Number.MAX_SAFE_INTEGER` 范围内的安全整数，总大小累加 MUST 不溢出安全整数。
- REQ-12：设备 ID、设备名、MIME 和文件标识 MUST 是有界字符串。文件名 MUST 是单个跨平台安全
  basename：不得为空、为 `.`/`..`、包含 NUL、控制字符、`/` 或 `\`，UTF-8 编码后不得超过
  255 bytes；在 Windows 上还 MUST 拒绝非法字符、保留设备名以及结尾空格或句点。
- REQ-13：接收端 MUST 证明最终路径位于当前下载目录的直接子级。文件名不得创建子目录，也不得
  通过绝对路径、路径穿越、平台分隔符或符号链接覆盖目录外目标。
- REQ-14：接收端 MUST 要求上传请求携带与已批准大小完全相等的有效 `Content-Length`。实际接收
  字节数 MUST 再独立计数；少于或超过声明值均 MUST 失败，且不得进入成功列表。
- REQ-15：接收内容 MUST 只被消费一次。成功前 MUST 写入下载目录内不可预测且独占创建的临时
  文件；失败、取消、超长、过短、服务停止或写入错误时 MUST 删除该临时文件。
- REQ-16：成功提交 MUST 不覆盖任何既有文件。最终命名继续采用原名、`name (1).ext`、
  `name (2).ext` 的规则，但提交操作 MUST 以“不存在才创建”的方式处理与其他进程或批次的竞态。
- REQ-17：一个文件失败或取消 MUST 不自动取消同批其他文件。发送端 MUST 对批内文件分别显示
  pending、sending 和终态；用户取消一个正在发送的文件时，只中止该文件。
- REQ-18：接收端 MUST 对同一时刻的确认对话框串行化；等待确认的批次数量 MUST 有界。超过上限
  的请求 MUST 返回可识别的“忙碌”响应，而不是继续弹窗或无限占用内存。
- REQ-19：文件传输 endpoint MUST 不启用 CORS。错误响应 MUST 使用稳定的错误码，使发送端区分
  拒绝、忙碌、非法请求、授权失败、过期、长度不符和服务器写入失败；响应和日志 MUST 不包含
  上传令牌、完整本地保存路径或超出调试需要的完整远端元数据。
- REQ-20：成功、失败、取消和过期 MUST 使接收端内存状态收敛；同一个文件不得同时出现在活动与
  完成列表。删除任务记录仍只删除 UI 记录，不删除已接收文件。
- REQ-21：零字节文件 MUST 可以成功传输。接收进度计算 MUST 不产生 `NaN` 或无限值。
- REQ-22：发送端批量请求、各文件上传及接收端写入 MUST 设置合理的网络/资源清理路径；组件卸载
  或服务停止后不得遗留活动控制器、定时器、写入流或待使用授权。
- REQ-23：用户拖入目录、不可读条目或其他无效选择时，发送端 MUST 显示可理解的提示并清空本次
  上传组件的内部候选列表；该预期拒绝不得作为 IPC handler 异常输出堆栈，紧接着拖入的合法普通
  文件 MUST 能独立登记，不得再次携带失败选择中的旧条目。
- REQ-24：已选状态 MUST 以“文件数”为第一行、“总大小 + 查看详情”为第二行；不得在摘要卡片内
  直接平铺文件名。查看详情 MUST 打开有界、可滚动的文件列表，长文件名截断并可查看完整名称，
  每个文件 MUST 可在发送前单独移除。摘要卡片相对外框的左、右、下边距 MUST 一致。
- REQ-25：`sending-list`、`sent-list`、`receiving-list`、`received-list` MUST 由主进程单向发布，
  renderer 不得把观察到的任务快照回写主进程。并发完成的每个文件 MUST 各自保留一个且仅一个
  终态记录；删除历史记录 MUST 通过按任务 ID 校验的显式 IPC 由主进程执行。
- REQ-26：发送端用户点击目标设备并成功发起批次时，活动区 MUST 立即切换到 Sending，不等待
  接收端确认或首个文件开始上传。
- REQ-27：接收端显示原生批次确认前，主窗口 MUST 显示、聚焦并导航到共享空间；主进程 SHOULD
  等待 renderer 确认导航已提交后再显示对话框，并设置有界超时避免 renderer 异常时永久阻塞。
  用户批准批次后，活动区 MUST 自动切换到 Receiving；拒绝时不得伪造接收任务。

## 用户流程与界面状态

1. 初始状态显示批量选择/拖拽入口。
2. 用户可一次选择或拖入多个普通文件；UI 显示文件数、总大小和“查看详情”，详情弹层中显示
   可滚动/截断的文件列表，并允许单独移除文件或清空本批选择。
3. 用户点击支持 `file-push-v2` 的在线设备。发送端立即锁定本批选择、切换到 Sending、创建每个
   文件的 pending 任务，并提交一次批量请求。
4. 接收端校验元数据：
   - 非法：不弹窗，发送端显示明确失败。
   - 正在处理其他确认且队列已满：不弹窗，发送端显示接收端忙碌。
   - 合法：接收端先显示并聚焦主窗口、进入共享空间，再弹出一次整批确认。
5. 用户拒绝时，发送端全部条目进入 rejected 终态；用户接受时，接收端切换到 Receiving，各文件
   开始上传。
6. 文件可以并行或顺序上传，但实现 MUST 限制并发，避免一次选择占满连接和文件句柄。初始实现
   的发送并发上限为 3。
7. 用户可单独取消活动文件；失败或取消不影响批内其他文件。
8. 接收端每个文件仍作为独立任务展示；成功后可在文件管理器中定位，失败/取消显示对应终态。
9. 批次完成后，选择区为空，用户可开始下一批。

禁用状态：

- 没有选择文件时不能发起批次。
- 不声明 `file-push-v2` 的设备不可作为文件传输目标，但共同支持时仍可共享剪贴板。
- 本地未启用文件接收时，批量请求直接返回禁用错误，不显示确认。

## 数据、接口与迁移

### HTTP 协议

- 新增批量申请 endpoint：
  `POST /api/file-batches`
- 新增单文件上传 endpoint：
  `PUT /api/file-batches/:batchId/files/:fileId`
- 批量申请请求包含固定协议版本、发送设备和文件元数据数组。
- 批量申请成功响应包含接收端 `batchId`，以及按 `fileId` 对应的上传令牌。
- 上传请求使用 `Authorization: Bearer <token>`，并携带精确 `Content-Length`。
- 删除：
  - `POST /api/upload/request`
  - `POST /api/upload/:uploadId`

具体 JSON 字段在实现时由共享 TypeScript 类型定义，但不得弱化 REQ-08 至 REQ-14 的约束。

### IPC / RemoteRef

- 不新增 renderer 系统权限或新的 IPC namespace。
- `receiving-list`、`received-list` 继续由主进程拥有，但项目类型增加批次标识、拒绝/取消/过期等
  必要终态。
- 四个传输任务 RemoteRef channel 均为主进程只读发布；renderer 删除 Sent/Received 历史时调用
  显式 share IPC，不再修改 RemoteRef 数组。
- 接收确认前主进程通过受控事件请求共享空间导航，renderer 完成路由更新后用带随机请求 ID 的
  share IPC 确认；该确认只接受主窗口 renderer。
- `share-capabilities` 的文件能力值从 `file-push` 迁移为 `file-push-v2`。

### 持久化 schema

- `capabilities` 仍为字符串数组，schema 形状不变。
- 初始化时将已有 `file-push` 替换为 `file-push-v2` 并去重；其余元素原样保留。

### 已有数据迁移

- 只迁移能力字符串，不迁移运行时任务或授权。
- 空、损坏或不含 `file-push` 的能力数组沿用现有 schema/default 处理。

### 回退/降级

- 新版不与旧版互传文件，不提供兼容 endpoint。
- 降级到旧版后，旧版不认识 `file-push-v2`，文件接收开关可能表现为关闭；这是本次接受的测试期
  兼容代价。剪贴板能力不受影响。

## 安全与隐私

- 所有 UDP 声明、批量元数据、路径参数、header 和文件 body 均视为不可信。
- 上传令牌只提供一次性批次授权，不证明设备身份；未使用 TLS 时，同网段能够观察流量的攻击者
  仍可能读取内容或令牌。
- 来源 IP 绑定减少令牌从另一主机重放的风险，但 NAT、代理或 IP 欺骗环境不等价于设备认证。
- 文件名校验、下载根边界、独占临时文件和不覆盖提交共同保护本地文件系统。
- 精确长度校验防止发送端以虚假小尺寸无限写入，但本次不提供磁盘配额；用户批准的大文件仍可能
  占满磁盘。
- CORS 移除后，普通网页不再得到跨域授权；服务仍面向同一局域网监听。
- info 日志只允许批次/传输短 ID、计数、大小、状态、耗时、MIME 和脱敏后的来源设备 ID。令牌、
  完整下载路径和完整远端文件名仅可在本地 debug 日志按现有隐私约束记录，错误响应不得回显。
- 临时文件名不得包含远端文件名或令牌；应用启动或服务启动时 SHOULD 清理能确定由 Bridge 创建且
  超过 24 小时的遗留临时文件，但不得删除无法证明归属的文件。

## 跨平台影响

### Windows

- 校验 `<>:"/\|?*`、控制字符、保留设备名以及结尾空格/句点。
- 验证同名递增、零字节文件、文件被占用、杀毒软件短暂占用和最终提交失败。
- 原生确认对话框、非原生标题栏和最小窗口尺寸需要手工验证。

### macOS

- `/`、NUL、控制字符和 255-byte 上限适用。
- 验证 Unicode 文件名、同名递增、原生确认焦点和 Finder 定位。

### Linux

- 即使文件系统允许反斜杠等字符，也使用共同的跨平台安全 basename 子集。
- 验证 Unicode 文件名、同名递增、原生确认焦点和文件管理器定位。

无法在当前平台完成的验证必须记为 `Not Verified`，不得用类型检查替代。

## 实现约束

- 文件系统、网络、授权、路径和原生确认必须留在主进程；renderer 不得直接获得 Node/Electron
  能力。
- 网络类型不能只依赖 TypeScript，必须在主进程做运行时校验。
- 上传 body 必须通过单一、可等待完成的 stream pipeline 写入，不得混用重复 `pipe` 与互相竞争的
  finish/error 处理器。
- 令牌比较 SHOULD 使用不泄露明显时序差异的方式；令牌不得进入 URL、RemoteRef 或日志。
- 临时文件必须位于下载目录内，以保证最终提交不跨文件系统。
- 不得修改同步模块、剪贴板内容语义、更新流程或发布配置。
- 若实现发现必须改变上述用户行为、安全边界、限制值或兼容策略，Spec 必须重新获得批准。

## 验收标准

- AC-01  
  Given 发送端选择 3 个合法文件并选择一个支持 `file-push-v2` 的设备  
  When 接收端批准该批次  
  Then 接收端只显示一次确认，3 个文件内容与大小完全一致地保存，发送与接收任务均正确收敛。

- AC-02  
  Given 同一批次包含零字节文件、Unicode 文件名和两个同名文件  
  When 接收端批准且目标目录已有同名文件  
  Then 零字节文件成功，既有文件不变，新文件使用无冲突递增名称且内容正确。

- AC-03  
  Given 批量元数据包含 `../x`、绝对路径、反斜杠路径、NUL、Windows 保留名、超长 UTF-8 文件名、
  非安全整数大小、重复 fileId、超过 256 个文件或超过 256 KiB body  
  When 请求到达接收端  
  Then 请求在弹窗和创建任何文件之前被拒绝，并返回稳定错误码。

- AC-04  
  Given 一个已批准文件令牌  
  When 从错误 IP、错误批次/文件使用，或并发/重复使用  
  Then 至多一个正确请求能开始写入，其余请求均在创建文件前失败。

- AC-05  
  Given 上传 `Content-Length` 缺失、非法、小于批准大小、大于批准大小，或实际 body 过短/过长  
  When 接收端处理上传  
  Then 文件失败、临时文件被清理、既有文件不变，且不会记录为成功。

- AC-06  
  Given 文件上传中途由发送端取消、连接断开、写入报错或共享服务停止  
  When 清理完成  
  Then 没有部分最终文件或遗留活动流，接收状态进入正确终态，批内其他文件不被自动取消。

- AC-07  
  Given 批次已批准但某文件 10 分钟内未开始上传  
  When 该令牌过期后再使用  
  Then 请求在创建文件前被拒绝，授权和 pending 状态从内存移除。

- AC-08  
  Given 接收端正在显示确认且等待队列达到上限  
  When 更多合法批次到达  
  Then 不新增对话框或无限等待，额外请求得到可识别的忙碌响应。

- AC-09  
  Given 一个旧版设备只声明 `file-push`，另一个新版设备声明 `file-push-v2`  
  When 双方发现彼此  
  Then 文件发送入口不可用且不尝试旧 endpoint；双方共同启用 `clipboard` 时剪贴板仍可共享。

- AC-10  
  Given 已有设置含 `file-push` 和 `clipboard`  
  When 新版首次初始化共享配置  
  Then 持久化能力变为去重后的 `file-push-v2` 与 `clipboard`，文件接收开关保持启用。

- AC-11  
  Given 用户拒绝整批、接收端禁用文件接收、接收端忙碌或请求非法  
  When 发送端收到响应  
  Then UI 分别显示可理解的拒绝、禁用、忙碌或非法请求状态，不将其混同为未知网络错误。

- AC-12  
  Given 批内有多个文件正在或等待发送  
  When 用户取消其中一个活动文件，另一个文件发生服务器错误  
  Then 其余文件继续，所有文件各自进入成功、失败、取消或拒绝终态，控制器和任务状态不泄漏。

- AC-13  
  Given 任一文件传输请求由浏览器跨域页面发起  
  When 页面发送预检或读取响应  
  Then 文件 endpoint 不返回 CORS 允许头，且不能借旧 endpoint 绕过新授权链路。

- AC-14  
  Given info 级日志和导出的诊断包  
  When 执行批准、上传、拒绝、失败、过期和取消场景  
  Then 其中不含上传令牌、完整下载路径或完整远端文件名，且仍能通过短 ID、大小和状态诊断问题。

- AC-15  
  Given 用户先拖入一个目录并收到不支持目录的提示  
  When 随后拖入一个合法普通文件  
  Then 目录候选已清空，普通文件成功登记，主进程不输出 `INVALID_FILE_SELECTION` handler 异常堆栈。

- AC-16  
  Given 用户选择多个文件  
  When 查看已选摘要并打开详情，再移除其中一个文件  
  Then 摘要两行分别显示文件数及“总大小 + 查看详情”，卡片左、右、下边距一致，详情列表可滚动且
  长文件名不破坏布局，被移除文件不再属于待发送批次，其余文件保持已选。

- AC-17  
  Given 接收端批准一个包含 10 个文件且发送并发上限为 3 的批次  
  When 10 个文件均成功落盘并完成  
  Then Receiving 收敛为空，Received 恰好保留 10 条对应成功记录，renderer 的旧快照不能覆盖
  主进程中的新记录；按 ID 删除其中一条只移除目标记录。

- AC-18  
  Given 发送端当前选择了文件，接收端当前位于非共享空间页面  
  When 发送端点击设备且接收端收到合法批次，随后用户批准  
  Then 发送端立即切到 Sending；接收端在原生确认出现前进入共享空间，批准后切到 Receiving。
